# แผนรองรับ PostgreSQL และติดตั้ง Shop บน Windows ภายในร้าน

วันที่ตรวจ: 24 ตุลาคม 2569 (Asia/Bangkok)

## ขอบเขตและสถานะ

ระยะ 1: ตรวจโครงสร้างและเตรียมเครื่องมือตรวจแหล่งข้อมูลแล้ว ยังไม่ได้เปลี่ยนฐานข้อมูลที่แอปใช้ และยังไม่มี PostgreSQL business adapter หรือตัวแปลงข้อมูลสำหรับใช้งานจริง

ความคืบหน้า 25 ตุลาคม 2569: แยกสัญญาข้อมูลธุรกิจกลาง 78 รายการแล้ว และเริ่มระยะ 2 ด้วยการแยก service/repository สำหรับรับเข้าสินค้า ดู [รายละเอียดและขอบเขตที่ยังเหลือ](STOCK_INTAKE_REFACTOR_TH.md) เส้นทางนี้ยังใช้ synchronous SQLite และยังเสียบ PostgreSQL แทนโดยตรงไม่ได้ แผนทดสอบเครื่องหลักหนึ่งเครื่องและเครื่องใช้งานอีกสองเครื่องอยู่ใน [คู่มือทดสอบภายในร้าน](LOCAL_THREE_MACHINE_TEST_TH.md)

ลูกค้าใช้หลายจุดขายผ่าน LAN โดยมี Windows เครื่องหลักหนึ่งเครื่องรัน Shop Server และ PostgreSQL เป็นบริการของ Windows เครื่องขายเข้า Shop ผ่านเบราว์เซอร์เท่านั้น ไม่เปิดไฟล์ฐานข้อมูลผ่านโฟลเดอร์แชร์ และไม่ต้องติดตั้ง PostgreSQL บนทุกจุดขาย Docker เป็นทางเลือกสำหรับทีมพัฒนา ไม่ใช่ข้อบังคับของลูกค้า

## สิ่งที่ตรวจพบในโค้ดปัจจุบัน

- `server/sqliteStore.ts` มีตารางธุรกิจ 25 ตารางในฐานใหม่, การเรียก `.prepare()` 276 จุด, `runInTransaction()` 32 จุด และการอ่าน `lastInsertRowid` 11 จุด ณ รุ่นที่ตรวจ การเปลี่ยนฐานจึงเกินกว่าการแก้ connection string
- `server/welfareStore.ts` เปิด SQLite แบบ synchronous; `server/routers.ts`, การยืนยัน session และงานตามเวลายังเรียกฟังก์ชัน store นี้
- `server/db.ts`, `drizzle/schema.ts` และ `drizzle.config.ts` เป็นเส้นทาง MySQL สำหรับบัญชี OAuth แยกจากฐานธุรกิจ ไม่ใช่ schema สินค้า/สมาชิกสำหรับ PostgreSQL คำสั่ง `db:push` ปัจจุบันยังเป็น MySQL ห้ามใช้กับฐานเป้าหมาย PostgreSQL
- ธุรกรรมปัจจุบันใช้ `BEGIN/COMMIT/ROLLBACK` และคำสั่ง synchronous; มี SQL เฉพาะ SQLite เช่น PRAGMA, `INSERT OR IGNORE`, `instr`, การรวมข้อความ และการจัดการวันที่
- ยอดบางส่วนใช้ `REAL` ส่วนมูลค่าราย Lot และการตัดต้นทุนใช้จำนวนเต็มสตางค์ ต้องรักษากฎปัดเศษเดิม ไม่เปลี่ยนสูตรระหว่างย้ายฐาน
- รหัสสินค้า สมาชิก บัตร และ HN เป็นข้อความ ต้องรักษาศูนย์นำหน้า; วันที่ธุรกิจเดิมเก็บเป็นข้อความตามเวลาไทย
- รหัส retry ของบิลและธุรกรรมสมาชิกมี index แบบไม่ unique การตรวจแล้วค่อย insert ซึ่งทำงานตามลำดับใน SQLite ไม่พอสำหรับ connection หลายตัวใน PostgreSQL
- ชุดสำรองและกู้คืนปัจจุบันเป็น SQLite จึงใช้แทน `pg_dump` / `pg_restore` ไม่ได้

## เครื่องมือตรวจแหล่งข้อมูลระยะ 1

```powershell
pnpm db:postgres:preflight --help
pnpm db:postgres:preflight --source "D:\ShopBackup\verified-backup.sqlite" --out "migration-reports\preflight.json"
```

ใช้ไฟล์สำรองที่ตรวจสอบแล้ว ตาม [ขั้นตอนสำรองและกู้คืน](BACKUP_RESTORE_SOP_TH.md) ไม่คัดลอกเฉพาะไฟล์ SQLite ขณะเปิดใช้งานจนข้อมูลใน WAL ขาดหาย ถ้าสำรองเข้ารหัส ให้เตรียมสำเนาที่ถอดรหัสอย่างถูกต้องก่อนตรวจ

เครื่องมือ:

- บังคับระบุ `--source`; ไม่อ่าน `SQLITE_DB_PATH` หรือ `DATABASE_URL` อัตโนมัติ และไม่สร้างไฟล์ฐานใหม่เมื่อสะกดชื่อผิด
- เปิด `readOnly`, อ่านภายใน transaction เดียว และไม่เรียก migration หรือ seed ของ Shop
- รายงานจำนวนแถวเป็นข้อความตัวเลข, โครงสร้างคอลัมน์/constraint, foreign keys, indexes, views, triggers และ fingerprint ของ schema
- ตรวจ `quick_check`, foreign-key violations, ตารางธุรกิจหลักที่หาย และกลุ่มรหัส retry ซ้ำโดยไม่ส่งออกรหัสเหล่านั้น
- แจ้งข้อมูลต้นทุนเก่าที่ไม่ทราบเป็น `review`; ไม่แทน `NULL` ด้วยศูนย์และไม่แก้ข้อมูลให้เอง
- ไม่ส่งออกข้อมูลรายแถว เช่น ชื่อสมาชิก เลขบัตร รหัสผ่าน session หรือสินค้า แต่รายงานยังเป็นข้อมูลภายในเพราะมี schema และจำนวนแถว โฟลเดอร์ `migration-reports/` ถูกตัดออกจาก Git
- ไม่เขียนทับไฟล์รายงานเดิมหรือไฟล์ฐานต้นทาง

Exit code: `0` = ตรวจแหล่งข้อมูลผ่าน, `2` = พบ source blocker, `1` = เปิดไฟล์/อาร์กิวเมนต์/เขียนรายงานไม่สำเร็จ **Exit 0 ไม่ได้หมายความว่า PostgreSQL พร้อมใช้งาน** ให้ดู `postgresReady:false` และ `implementationBlockers` ด้วย

เครื่องมือนี้ยังไม่ส่งออก/นำเข้าแถวข้อมูล, ไม่สร้าง PostgreSQL schema, ไม่ตรวจยอดเงินและสต็อกเทียบฐานปลายทาง และไม่รับรองว่าฐานเก่าทุกรุ่นแปลงได้ ขั้นตอนเหล่านี้เป็นเกณฑ์บังคับในระยะถัดไป

## แบบฐานและ repository เป้าหมาย

- ใช้ PostgreSQL รุ่น major ที่ยังได้รับการสนับสนุนและ pin เวอร์ชันสำหรับชุดติดตั้ง ไม่กำหนด dependency บน cloud service
- แอปใช้ role สิทธิ์จำกัด แยกจาก role สำหรับ migrations; PostgreSQL อยู่บนเครื่องหลักและไม่เปิดให้จุดขายเชื่อมตรง
- ใช้ connection pool จำนวนจำกัด เริ่มจากค่าขนาดเล็กแล้ววัดจริง แต่ละ transaction ต้องยืม connection เดียวและส่ง context เดียวให้ทุก repository ห้ามสลับไปเรียก pool กลางกลางธุรกรรม
- เปลี่ยน `?` เป็น parameter ของ driver, `lastInsertRowid` เป็น `INSERT ... RETURNING`, `INSERT OR IGNORE` เป็น `ON CONFLICT`, และเขียน SQL วันที่/ค้นหาใหม่ตาม semantics เดิม พร้อมทดสอบภาษาไทย
- ใช้ versioned migrations แยกจาก MySQL/OAuth เดิม; การทำ schema ของ SQLite ขณะเปิดแอปไม่ถูกนำไปใช้กับ PostgreSQL
- รักษา ID เดิมตอนย้าย แล้วตั้ง identity sequence ให้เริ่มหลัง ID สูงสุด ห้ามปล่อย driver แปลง `bigint`/`numeric` เป็น JavaScript Number โดยไม่ตรวจช่วงและความแม่นยำ
- แบบชนิดข้อมูลที่จะยืนยันกับ fixture: ยอดเงิน `numeric(20,2)`, ต้นทุนต่อหน่วย `numeric(24,10)`, ฟิลด์ `*_satang` เป็น `bigint`, สถานะเปิด/ปิดเป็น boolean, รหัสที่มีศูนย์นำหน้าเป็น text, JSON มี mapping และ validation ชัดเจน ถ้าต้นทางมีทศนิยมเกินข้อกำหนดต้องออกรายงานให้ตัดสินใจ ไม่ปัดเงียบ ๆ
- เลือกแปลงเวลาข้อความไทยเป็น instant ด้วย Asia/Bangkok อย่างชัดเจน แล้วใช้ `timestamptz` สำหรับเหตุการณ์ และ `date` สำหรับวันหมดอายุ ทดสอบย้อนหลังและรอบตัดยอดก่อนยืนยันการแปลง
- สร้าง indexes ตามการค้นหาจริง เช่น วันที่/เลขบิล, สมาชิก+วันที่, สินค้า+ลำดับ FIFO, card/session ที่เปิดอยู่ และ foreign-key ฝั่งอ้างอิง ใช้ EXPLAIN กับข้อมูลจำลองขนาดใหญ่ก่อนกำหนดจำนวน indexes

## ความถูกต้องเมื่อหลายเครื่องทำรายการพร้อมกัน

- ยอดเงินสมาชิก: lock แถวสมาชิกหรือใช้ conditional UPDATE ให้ตรวจและหักใน transaction เดียว; ห้ามอ่านยอดออกมาคำนวณแล้วเขียนโดยไม่มีการป้องกัน
- สต็อก/FIFO: lock สินค้าและ Lot ตามลำดับแน่นอน เช่น product ID แล้ว lot ID; ตรวจจำนวนที่เหลือภายใน transaction เดียวกับบิลและการตัดต้นทุน
- Retry: เพิ่ม unique constraint สำหรับ request ID ที่ใช้งานจริงพร้อมตรวจ payload fingerprint; request เดิมต้องคืนคำตอบเดิม และ request ID เดิมกับ payload ใหม่ต้องปฏิเสธ การไม่มี request ID ในบิลเก่าต้องยังย้ายได้
- เลขบิล: แทนการอ่าน MAX แล้วบวกด้วยตัวนับประจำวันที่ lock ได้/sequence ที่เหมาะสม ไม่ใช้เลข id เป็นการรับประกันว่าเลขเอกสารต่อเนื่องไม่มีช่องว่าง
- Retry deadlock/serialization เฉพาะธุรกรรมที่ปลอดภัย จำนวนครั้งจำกัด และใช้ request ID เดิม ไม่มีการส่งงานพิมพ์ก่อน commit
- บิล รายการย่อย เงินสมาชิก สต็อก allocations มูลค่า และ audit log ต้องสำเร็จหรือ rollback พร้อมกัน
- คืนบัตร/ผูกบัตร: รักษา unique partial index ของรอบบัตรที่ยังไม่ปิด และป้องกันผูกบัตรเดียวกับสองสมาชิกพร้อมกัน

## การย้ายข้อมูลและ rollback

1. ซ้อมจากไฟล์สำรองในฐาน PostgreSQL แยก ห้ามทดลองกับฐานร้านที่กำลังใช้งาน
2. จัดทำ manifest และ checksum ของไฟล์ต้นทาง; บันทึก schema fingerprint, release และเวลาที่สำรอง
3. นำเข้าตาม dependency ของ FK, คง IDs/เลขเอกสาร/ศูนย์นำหน้า/ค่า NULL, ตั้ง sequence และตรวจ constraints หลังโหลด
4. เทียบ counts ทุกตาราง, ยอดเงินสมาชิกเป็นรายคน, ผลรวมบัญชี, บิลและรายการย่อย, stock ต่อสินค้าและ Lot, received/remaining value, allocations, refund และ audit history พร้อมรายการที่ไม่ทราบต้นทุนเดิม
5. ทดสอบข้อมูลไทย ค่าว่าง เงินศูนย์ ยอดใหญ่ วันหมดอายุ พ.ศ./ค.ศ. และรอบตัดยอด ข้อมูลการเข้าสู่ระบบและ hash รหัสผ่านต้องคง semantics เดิม; session เดิมอาจให้ล็อกอินใหม่ตามนโยบายที่กำหนด ไม่ส่งออก secret ผ่านรายงาน
6. วันย้ายจริงหยุดรับรายการชั่วคราว สำรองอีกครั้งและย้ายจาก snapshot ล่าสุด ตรวจยอดก่อนเปลี่ยน provider
7. เก็บ SQLite snapshot ไว้เป็นต้นทางย้อนกลับ ถ้า PostgreSQL ยังไม่รับธุรกรรมใหม่สามารถกลับ release เดิมและฐานเดิมได้ แต่หลังเปิดขายบน PostgreSQLแล้วห้ามย้อนกลับไปไฟล์เก่าโดยตรง ต้องมีแผน replay/reverse migration หรือกู้คืนที่รักษาธุรกรรมใหม่
8. หลังย้าย ใช้ `pg_dump` และทดสอบ `pg_restore` เป็นประจำ การตั้ง key/ไฟล์แนบ/ภาพ/ใบรับรอง/ค่าบริการ Windows ต้องอยู่ในแผนสำรองทั้งระบบ ไม่ใช่เฉพาะไฟล์ฐาน

## Windows และ Setup ที่เตรียมควบคู่ได้

- โปรแกรมกับข้อมูลคนละโฟลเดอร์: Program Files สำหรับ release, ProgramData สำหรับ config/data/logs และสำรองต่างอุปกรณ์
- Windows services เปิดเองโดยไม่ต้องมีผู้ใช้ล็อกอิน; แยกบัญชีบริการและสิทธิ์เข้าถึงไฟล์ให้พอดี ไม่ใช้รหัสฐานข้อมูลฝังใน repository
- จำกัด Setup ครั้งแรกให้ผู้ดูแลบนเครื่องหลักผ่านรหัสติดตั้งครั้งเดียว และป้องกันการสร้างผู้บริหารคนแรกพร้อมกันจากหลายเครื่อง ไม่เปิดให้ผู้ใช้ LAN คนอื่นยึดการตั้งค่าก่อนเจ้าของ
- Wizard ครั้งแรกให้ผู้ดูแลตั้งชื่อร้านและบัญชีผู้บริหาร แล้วนำเข้าไฟล์ตัวอย่างสมาชิก/สินค้าแบบ preview/validate/confirm; ข้ามและกลับมาทำต่อได้
- ตรวจรหัสซ้ำ เงินและสต็อกตั้งต้นก่อนนำเข้า พร้อม transaction และ idempotency ป้องกันอัปโหลดซ้ำเพิ่มยอดซ้ำ
- การอัปเดตใช้ฐานเดิมต่อและสำรองก่อน migration; ห้าม installer ล้างข้อมูลหรือรัน Setup ทับบัญชีเดิม
- เครื่องขายลงทะเบียนจุดขายต่อเบราว์เซอร์และติดตั้ง Printer Helper ที่เครื่องต่อเครื่องพิมพ์ ทดสอบ LAN/HTTPS และอินเทอร์เน็ตขาดแยกจากเครือข่าย LAN ขาด

## เกณฑ์เปิดให้ลูกค้าใช้

ต้องผ่าน PostgreSQL integration tests และการทดสอบบน Windows จริง ไม่ใช้ผลทดสอบ SQLite หรือการ build ผ่านแทน ได้แก่ สองเครื่องแย่งสินค้าชิ้นสุดท้าย, ใช้ยอดสมาชิกเดียวกันพร้อมกัน, retry หลัง connection หลุด, request ID ซ้ำคนละ payload, เปิดร้านใหม่โดยไม่มีเดโม, อัปโหลดซ้ำ, service restart, backup/restore และ update/rollback โดยข้อมูลไม่สูญหาย
