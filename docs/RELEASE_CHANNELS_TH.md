# แยกการออกเวอร์ชัน Railway และ Windows Final

ใช้โค้ดร่วมกัน แต่แยก branch ที่ปล่อยใช้งาน การตั้งค่า และฐานข้อมูลของแต่ละเป้าหมาย

## ช่องทางออกเวอร์ชัน

| ช่องทาง | Branch | คำสั่งเริ่มระบบ | นโยบาย |
|---|---|---|---|
| Railway ที่ผู้ใช้ใช้งาน | `main` | `pnpm start:railway` | `railway-live` |
| เตรียมปิดงาน Final | `main-v2` | รอรวมงานและตรวจรับก่อนปล่อย | เตรียมใช้ `windows-final` |
| ลูกค้าทดสอบ Local/LAN | `main` | `pnpm.cmd test:lan:live` | `railway-live` บน `.lan-test` |

`main` เป็นชุดที่ให้ลูกค้าทดสอบใช้งานจริง ทั้ง Railway และ Local ส่วน `main-v2` เป็นสายเตรียมปิดงาน Final ยังไม่ใช่เวอร์ชันส่งมอบ ทั้งสองสายมีประวัติต่างกัน ต้องตรวจและรวมงานเดิมก่อนปิด Final ไม่เขียนทับหรือ force-push ข้ามงานเดิม รอบนี้ยังไม่เปลี่ยนโค้ดใน `main-v2` ส่วน branch `release/windows-final` และ `test/windows-lan` ที่สร้างไว้ก่อนยืนยันชื่อเป็นเพียง snapshot ไม่ใช่ช่องทางอัปเดตที่ให้ลูกค้าใช้

## นโยบายการใช้งาน

| เงื่อนไข | Railway | Windows Final |
|---|---|---|
| ลงทะเบียนจุดขายก่อนชำระเงิน | ไม่บังคับ หากลงทะเบียนไว้แล้วจะยังบันทึกเลขจุดขายเดิม | บังคับทั้งหน้าจอและ API |
| เปลี่ยนรหัสผ่านครั้งแรก | ไม่แสดงหน้าบังคับ บัญชีและรหัสผ่านเดิมใช้ต่อได้ | บังคับตามสถานะบัญชีเดิม |
| แพ็กเกจ/ทดลองใช้ | เปิดฟีเจอร์ทั้งหมด ไม่มีวันหมดช่วงทดลองมาขวาง | ตรวจ license/ช่วงทดลองตามปกติ |
| ล็อกอินและสิทธิ์ตามบทบาท | คงเดิม | คงเดิม |
| ตรวจยอดเงิน สต็อก และป้องกันรายการซ้ำ | คงเดิม | คงเดิม |

นโยบายอ่านจาก `SHOP_RELEASE_CHANNEL` บน server เท่านั้น ไม่เชื่อค่าที่ browser ส่งมา และไม่เขียนทับ flag บัญชี, license, trialStart หรือข้อมูลจุดขายในฐานข้อมูล เมื่อใช้ช่องทาง Final จะอ่านข้อกำหนดจากข้อมูลเดิมได้อีกครั้ง ไม่ใช่การปลดล็อกด้วยการแก้ข้อมูลลูกค้า

- `start:railway` กำหนด `DEPLOYMENT_MODE=cloud`, `CLOUD_PROVIDER=railway`, `SHOP_RELEASE_CHANNEL=railway-live`
- `start:windows` กำหนด `DEPLOYMENT_MODE=onpremise`, `SHOP_RELEASE_CHANNEL=windows-final`
- `pnpm start` เดิมยังรันได้ หากไม่กำหนดช่องทางจะคงนโยบายเดิม (`legacy`) ค่าช่องทางที่สะกดผิดจะทำให้เริ่มระบบไม่สำเร็จแทนการปลดเงื่อนไขเงียบ ๆ

`railway.json` ใช้ `pnpm start:railway` แล้ว หลัง deploy ตรวจ startup log ว่ามี `channel=railway-live` หาก service มี Start Command ที่กำหนดเอง ต้องใช้คำสั่งนี้หรือกำหนด Variable `SHOP_RELEASE_CHANNEL=railway-live` ให้ตรงกัน โค้ดใน GitHub ไม่สามารถยืนยันแทนสถานะ deployment จริงบน Railway ได้

## ขั้นตอนนำฟีเจอร์ขึ้น Railway

1. ตรวจว่า Railway service ชี้ `main` และตรวจ commit ที่กำลังปล่อยทุกครั้ง
2. ทำงานข้อบังคับ/ตัวติดตั้งเพื่อปิด Final ใน `main-v2` ไม่ push งานชุดติดตั้งเข้า branch ที่ Railway auto-deploy
3. แยก commit ของฟีเจอร์ร่วมออกจาก commit ของข้อบังคับชุดติดตั้ง เลือกเฉพาะฟีเจอร์ที่ต้องการไปสาย Railway และตรวจ dependency ของ commit ด้วย
4. ทดสอบบน staging ซึ่งใช้ฐานข้อมูลจำลองหรือสำเนาที่แยกจาก production และ secret คนละชุด ห้ามชี้ staging ไปที่ Volume จริง
5. ก่อนปล่อย ตรวจ diff, schema migration, สำรอง SQLite ด้วยเครื่องมือสำรองของระบบ และตรวจไฟล์สำรอง การอัปเดตหน้าจอไม่ควรมีการนำเข้าหรือรีเซ็ตข้อมูล
6. ปล่อย commit ที่ตรวจแล้ว ตรวจล็อกอิน/ขาย/สมาชิก/สต็อกตามบทบาทเดิม เก็บ commit ก่อนปล่อยไว้สำหรับย้อนโค้ด

การย้อนโค้ดกับการกู้ข้อมูลเป็นคนละงาน ห้าม restore ฐานข้อมูลเก่าทับรายการขายใหม่โดยอัตโนมัติ หากมี migration ต้องตรวจว่าโค้ดรุ่นก่อนอ่าน schema ใหม่ได้ด้วย

## ข้อบังคับกับความปลอดภัย

ข้อกำหนดการติดตั้งหรือแพ็กเกจสามารถแยกนโยบายตามช่องทางได้หลังยืนยันรายการ แต่การล็อกอิน สิทธิ์ตามบทบาท การตรวจยอดเงิน/สต็อก และการป้องกันรายการซ้ำต้องคงอยู่ทั้งสองช่องทาง ค่าที่เปิดฟีเจอร์ทางหน้าจอต้องตรงกับการตรวจฝั่งเซิร์ฟเวอร์ ไม่ใช้เพียงซ่อนปุ่ม และไม่แก้สถานะบัญชีหรือ license ในฐานข้อมูลเพื่อทำให้โหมดดูเหมือนผ่านเงื่อนไข

ไฟล์ `deploy/*.env.example` เป็นตัวอย่างอ้างอิง ไม่ใช่คำสั่งให้นำไปแทน Variables ของ Railway ระบบปัจจุบันยังใช้ SQLite การติดตั้ง PostgreSQL ไม่ได้ทำให้แอปเปลี่ยนฐานข้อมูลอัตโนมัติ
