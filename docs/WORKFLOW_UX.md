# รูปแบบงานและการตรวจ UI/UX

## รับเข้าสินค้า

เปิดเมนู **รับเข้าสินค้า** ได้โดยตรง หรือใช้ปุ่มรับเข้าจากสต็อก/ทางลัด POS
เลือกสินค้าเดิมหรือเพิ่มสินค้าใหม่ในขั้นตอนเดียว กรอกจำนวนซื้อ ของแถม ยอดจ่าย Lot และวันหมดอายุ แล้วเพิ่มลงรายการรับเข้ารอบนี้
สินค้าใหม่ยังเป็น draft จนกว่าจะยืนยันรับเข้าทั้งชุด Backend บันทึกสินค้าใหม่กับสต็อกใน transaction เดียวตามของเดิม
การสร้างสินค้าใหม่ต้องใช้สิทธิ์ผู้บริหาร ส่วนพนักงานรับเข้าสินค้าเดิมตามสิทธิ์ที่มีได้

ก่อนบันทึกมีสรุปให้ยืนยัน หลังสำเร็จมีผลรายการกลางจอและปุ่มรับเข้ารอบใหม่
การเปลี่ยนหน้าเมื่อมี draft ต้องยืนยันว่าจะทิ้ง; refresh/ปิดแท็บใช้การเตือนมาตรฐานของ browser
Dialog รับเข้าอยู่ใน portal นอก page transform เพื่อไม่ให้ปุ่มบันทึกหลุดขอบจอ

## การขายและเอกสาร

1. ตรวจยอดและวิธีชำระใน dialog ก่อนยืนยัน
2. รอผล server; ปุ่มถูกล็อกระหว่างบันทึก
3. หน้าจ่ายสำเร็จแสดงใบเสร็จและทางเลือก **พิมพ์และกลับ POS** / **ไม่พิมพ์และกลับ POS**
4. เมื่อจบ ให้ล้างบิลและโฟกัสช่องสแกน พร้อมรายการถัดไป

ความล้มเหลวของเอกสารไม่ย้อนสถานะการขาย แสดงข้อความภายในผลรายการเดิมและลองพิมพ์ใหม่ได้โดยไม่เรียก checkout ซ้ำ
Helper ตอบรับหมายถึง “ส่งงานพิมพ์แล้ว” ไม่ยืนยันกระดาษออก Browser print รอ afterprint (รวมการกดยกเลิก) และบอกเพียงว่ากลับจากหน้าต่างพิมพ์แล้ว
หากพิมพ์ซ้ำจากประวัติ เมื่อจบให้กลับหน้ารายงานเดิม ไม่ล้าง POS เหมือนการขายใหม่
Enter ทำหน้าที่ของปุ่มที่โฟกัส ไม่ดัก Enter ทุกปุ่มไปสั่งพิมพ์

## สีและการแจ้งผล

สีแบรนด์แยกจาก `--action-bg`/`--action-ink` (ส้มอ่อน/ตัวอักษรส้มเข้ม), `--success-bg`/`--success-ink` (เขียวอ่อน/ตัวอักษรเขียวเข้ม), warning (เหลือง) และ error/danger (แดง)
Disabled ใช้สีเทากับข้อความสาเหตุ ไม่มีเครื่องหมายสำเร็จบนปุ่มก่อนจ่าย
ปุ่มปิดธรรมดาใช้สีเป็นกลาง ส่วน export แยกสีตามประเภทไฟล์ ขอบปกติ 1px และ focus ring ชั้นเดียว 2px

`WorkflowDialog` ใช้ portal, focus trap, Escape, คืนโฟกัส และป้องกัน outside click ที่ทำให้ draft หาย
`ConfirmDialog` ใช้สำหรับตัดสินใจก่อนเปลี่ยนข้อมูลสำคัญ
`WorkflowResult` หรือ `notify.completed` ใช้ผลสำเร็จสำคัญที่ต้องรับทราบ
`notify.error`/`notify.warning` ใช้ข้อความกลางจอที่ผู้ใช้ต้องหยุดแก้; รายละเอียดแก้ไขยังอยู่ใกล้ช่องกรอก
Toast เหมาะกับข้อมูลทั่วไป ไม่ต้องยืนยัน และไม่ซ้ำกับผลธุรกรรมใน dialog

## สมาชิกเดิมกลับมาใช้บริการ

เมื่อข้อมูลระหว่างสมัครตรงกับสมาชิกเดิม Dialog ต้องให้เลือกสมาชิกแต่ละรายและทำต่อได้ ก่อนตรวจบัตรว่างหรือเงินเริ่มต้นของการสมัครใหม่
จาก POS สมาชิกที่บัตรพร้อมใช้จะไปยืนยันข้อมูลก่อนเข้าบิล สมาชิกที่ยังไม่มีบัตรจะไปจ่ายบัตรให้หมายเลขเดิมด้วยขั้นตรวจสอบและยืนยันของระบบบัตร
หากสถานะสมาชิกถูกระงับหรือมีบัตรที่ไม่พร้อมใช้ ให้เปิดหน้ารายละเอียดเพื่อตรวจสอบ ไม่ปลดระงับอัตโนมัติ
จากหน้าสมาชิก ให้เปิดรายละเอียดสมาชิกที่เลือกเพื่อทำรายการต่อ

อ่านสถานะล่าสุดเมื่อเลือกสมาชิก หากอ่านไม่ได้ต้องคงฟอร์มและรายชื่อไว้ให้ลองใหม่ การเลือกบัญชีเดิมไม่คัดลอกชื่อ รูป หรือเงินเริ่มต้นจากฟอร์มสมัครเข้าไปทับ และไม่สร้างสมาชิกใหม่
กรณีเป็นคนละคน อนุญาตให้ยืนยันสมัครใหม่เมื่อชื่อหรือเบอร์โทรซ้ำเท่านั้น เลขประชาชนหรือบัตรที่ผูกอยู่แล้วต้องใช้บัญชีเดิมหรือแก้ข้อมูล

หาก POS มีสินค้าในบิลอยู่และต้องเปิดข้อมูลสมาชิก ให้ยืนยันพักบิลก่อนออกจากหน้า โดยบันทึกบิลลงเครื่องให้สำเร็จก่อนนำทาง หากบิลที่พักเต็มหรือพื้นที่จัดเก็บมีปัญหา ต้องคงบิลปัจจุบันไว้


## สีและการบันทึกการตั้งค่า

ใช้พื้นขาว ส้มอ่อนสำหรับปุ่มดำเนินการทั่วไปและการนำทาง และเขียวอ่อน สำหรับผลสำเร็จที่ server ยืนยันแล้ว สีชนิดไฟล์ยังแยกกัน: CSV ฟ้า, Excel เขียว, PDF แดง, พิมพ์ม่วง
หน้าตั้งค่าไม่มีแถบยืนยันลอยด้านล่าง ปุ่มบันทึกด้านบนเปิด Dialog กลางจอพร้อมรายชื่อส่วนที่เปลี่ยน กดยืนยันจึงบันทึกจริง และแสดง Dialog สำเร็จสีเขียวอ่อนหลังบันทึกแล้วเท่านั้น

Dialog ผลรายการใช้กล่องขาวกลางจอตามภาพอ้างอิงของผู้ใช้ ฉากหลังมืดลงโดยไม่เบลอ ไอคอนสถานะขนาดใหญ่แบบเส้น ข้อความบอกผลสั้นชัด และปุ่มรับทราบเพียงปุ่มเดียว สีเขียวอ่อน ใช้กับผลสำเร็จ

การยืนยันและผลรายการใช้ FeedbackDialog ตัวเดียวกัน: ขนาดกล่อง ระยะห่าง ตำแหน่งหัวข้อ และตำแหน่งปุ่มคงเดิม เปลี่ยนไอคอน/สี/ข้อความตามหน้าที่ ยืนยันทั่วไปใช้เครื่องหมายคำถามส้ม, สำเร็จใช้ถูกเขียว, เตือนใช้สามเหลี่ยมส้ม, การกระทำที่เสี่ยงต่อข้อมูลใช้เครื่องหมายเตือนแดง, ผิดพลาดใช้กากบาทแดง ปุ่มยกเลิกใช้สีกลางเสมอ

ปุ่มจบงานใช้เขียวอ่อน ปุ่มถอนเงิน/คืนเงิน/ปิดรอบและระงับใช้งานใช้คำเตือนส้ม ปุ่มลบใช้แดงชัดเจน สวิตช์เปิด–ปิดคงรูปแบบเดิม ข้อความร่างข้อมูลและเริ่มดาวน์โหลดเป็นข้อมูลทั่วไป ไม่ใช้สีสำเร็จก่อนบันทึกจริง

หน้ารายละเอียดสินค้าเปลี่ยนเป็นฟอร์มแก้ไขโดยปิดหน้ารายละเอียดก่อน ฟอร์มแก้ไขและนับสต็อกใช้ WorkflowDialog/Portal เหมือนกัน จึงไม่ถูกหน้ารายละเอียดบัง ฉากบังเป็นดำโปร่งแสงสีกลาง ไม่มีสีน้ำเงินเทาหรือ blur ทับสีปุ่ม

สีตามคำขอล่าสุด: สีหลักเมนู/แท็บและปุ่มทั่วไปเป็นส้มอ่อน #FFEDD5 ตัวอักษรส้มเข้ม #9A3412 สีสำเร็จใช้เขียวอ่อน #65DC98 พร้อมตัวอักษรเขียวเข้ม #052E16 เพื่อให้อ่านชัด สีเตือน อันตราย ประเภทไฟล์ และสวิตช์เดิมคงตามหน้าที่

## การจัดหน้า POS

ช่องสแกนใช้เส้นโฟกัสสีกลางบางที่กรอบนอกเพียงเส้นเดียว ปุ่มเงินสด/QR/หักบัญชีอยู่ด้านล่างของแผงสรุปบนจอ desktop แผงลัดแสดงสินค้าคอลัมน์เดียว รูปอยู่ซ้าย ชื่อและจำนวนอยู่กลาง ราคาอยู่ขวา สินค้าขายหลายขนาดยังมีปุ่มราคาแยกด้านล่างให้กดได้ครบ

## คำเตือนก่อนจ่ายบัตร

เมื่อยืนยันสมาชิกที่ยังไม่มีบัตรหรือบัตรไม่พร้อมใช้งาน ให้แสดงคำเตือนเพียงหน้าต่างเดียวก่อน เปิดฟอร์มจ่าย/เปลี่ยนบัตรใน `onAcknowledge` ของคำเตือนเท่านั้น ทั้งทางผูกบิลและกระเป๋าเงิน การเปิดทั้งสองหน้าต่างในรอบ render เดียวกันทำให้ลำดับการรับ pointer/focus ของ Radix ไม่ตรงกับ z-index ที่มองเห็น ปุ่มรับทราบจึงกดไม่ได้แม้เห็นอยู่ด้านบน

## ความยาวใบเสร็จและการเลือกกระดาษ

Local Printer Helper ใช้ความสูงที่วัดจากเอกสารแยก ณ ความกว้างพิมพ์จริง โดยเปิด CSS สำหรับพิมพ์และรอฟอนต์/รูปพร้อมก่อนวัด ไม่ใช้สัดส่วนความกว้างบนหน้าจอเพื่อคาดเดาความสูง การพิมพ์ผ่าน browser ใช้ `@page size:auto` เพื่อให้ขนาดกระดาษในไดรเวอร์ เช่น 80 × 200 มม. เป็นตัวกำหนดจุดแบ่งหน้า แอปยังกำหนดความกว้างเนื้อหาและขอบตามโปรไฟล์ที่เลือก ใบยาวเกินกระดาษแบ่งต่อได้ โดยไม่บังคับเก็บทั้งเอกสารไว้ในหน้าเดียว

ตรวจ PDF แยกที่ขนาด 58/72/80 มม. ทั้งใบสั้นและใบยาว ด้วย `node --import tsx scripts/thermal-pagination-smoke.mjs <receipt-helper.html จาก workflow smoke>` ตรวจจำนวนหน้า รายการทุกแถว และข้อความท้ายเอกสาร

สถานะตั้งค่าที่ยังไม่บันทึกแสดงข้อความสั้นข้างปุ่มบันทึก ไม่ใช้แถบเตือนเต็มหน้าและไม่เปิด Dialog เมื่อสลับตัวเลือก ขั้นตรวจทานเริ่มเมื่อผู้ใช้กดบันทึกจริง

## หน้าคืนบัตร

POS ใช้ ReturnCardModal: สแกน/ค้นหาสมาชิก → ตรวจสอบชื่อ เลขบัตรและเงินคืน → ยืนยันในกรอบกลาง โดยช่องค้นหาไม่เสนอ “บุคคลทั่วไป” พื้นที่เริ่มต้นอธิบายขั้นตอนและรองรับเครื่องสแกน/กล้อง พนักงานต้องทำเครื่องหมายว่าได้รับบัตรจริงก่อนเปิดขั้นยืนยัน รายละเอียดสมาชิกใช้หน้าตาเดียวกันพร้อมสมาชิกที่เลือกไว้แล้ว

ยอดศูนย์คืนบัตรได้โดยไม่สร้างธุรกรรมคืนเงิน การย้อนกลับ/ยกเลิกไม่เปลี่ยนข้อมูล ขณะส่งคำขอป้องกันกดซ้ำ และคง expectedSessionId กับ clientRequestId ของ API เดิม หลังสำเร็จปิดฟอร์มและแสดงผลเขียวอ่อน #65DC98 กลางจอ บัตรกลับเป็นว่างและประวัติสมาชิกยังอยู่

## QR รับเงิน: พร้อมเพย์และบัญชีธนาคาร

ตั้งค่า → การชำระเงิน เลือกช่องทาง QR เริ่มต้นได้ และเปลี่ยนช่องทางเฉพาะบิลได้ที่หน้ายืนยันชำระ POS รายการแสดงเฉพาะช่องทางที่เปิดใช้งาน

พร้อมเพย์สร้าง QR ระบุยอดจากหมายเลขพร้อมเพย์ตามเดิม บัญชีกรุงไทย (KTB), กสิกรไทย (KBANK), ไทยพาณิชย์ (SCB), ออมสิน (GSB) ใช้รูป QR รับเงินแบบไม่ระบุยอดที่ธนาคารออกให้ ตั้งค่ารูปครั้งแรกใน “แก้ไขบัญชี” ระบบอ่านและเก็บ payload ของ QR เดิม ไม่สร้าง QR จากเลขบัญชีเปล่า และไม่แก้ payload ธนาคารเพื่อแทรกยอด ลูกค้ากรอกยอดตามบิลในแอปธนาคาร

รูป PNG/JPG/WEBP ไม่เกิน 2MB ต้องถอดรหัสเป็น Thai payment QR ที่ CRC ถูกต้อง ปฏิเสธ QR เว็บไซต์, QR ตรวจสลิป, QR ระบุยอด และ QR ชั่วคราว โดยตรวจทั้ง browser และ API การตรวจนี้ยืนยันรูปแบบ QR เท่านั้น ผู้ตั้งค่าต้องตรวจชื่อผู้รับและบัญชีว่าตรงกับบัญชีที่กำหนดด้วย

การเปลี่ยนเลขบัญชีหรือธนาคารจะล้าง QR เดิมให้ตั้งใหม่ การสลับช่องทางชำระซ่อน QR เดิมทันทีและรีเซ็ตช่องยืนยันตรวจรับเงิน ใบแจ้งชำระใช้ QR ของช่องทางที่เลือก การเปลี่ยนช่องทางหรือพรีวิวใบแจ้งชำระไม่บันทึกยอดขาย ช่องทางที่ยังไม่ได้ตั้ง QR จะแจ้งเหตุผลแทนการใช้ QR ของอีกบัญชี บัญชีเก่าที่ไม่มี QR ยังคงรับโอนผ่านเลขบัญชีได้

Browser smoke ตรวจภาพ QR เทียบ payload ของทั้ง 4 ธนาคารและพร้อมเพย์ ตรวจการอ่านรูป, บันทึกการตั้งค่า, QR ในใบแจ้งชำระ และ viewport มือถือ โดยใช้ fixture แยกใน /tmp เท่านั้น ไม่ใช่การทดสอบโอนเงินจริงกับธนาคาร

## ต้นทุนขายและกำไร

ใช้ยอดต้นทุนที่บันทึกตอนขายจากล็อตรับเข้า เมื่อข้อมูลรับเข้าครอบคลุมจำนวนขายทั้งบรรทัด ต้องใช้ยอดนั้นแม้เป็น 0 บาท หรือต้นทุนเฉลี่ยต่อหน่วยในทะเบียนถูกล้าง/ปัดเศษเป็น 0 ไม่ใช้ราคาขายทับต้นทุนที่มีหลักฐานอยู่แล้ว รายงานรายวัน แยกสินค้า แยกหมวด และแยกผู้ขายใช้เงื่อนไขเดียวกัน

ตัวอย่างขาย 2 ชิ้น ราคาชิ้นละ 20 ต้นทุนชิ้นละ 17: ยอดขาย 40 ต้นทุน 34 กำไร 6 บาท หากทั้งสองชิ้นมาจากล็อตที่บันทึกรับเข้าต้นทุน 0 และลดราคา 1 บาท: ยอดขายสุทธิ 39 ต้นทุน 0 กำไร 39 บาท รายละเอียดแยกสินค้า/หมวดยังคงแสดงยอดและกำไรก่อนส่วนลดตามหัวตาราง ข้อมูลเก่าที่ยังไม่มีต้นทุนยืนยันยังใช้ราคาขายประเมินตามนโยบายเดิม ส่วนยอดขาดทุนจากการขายต่ำกว่าต้นทุนจริงยังแสดงติดลบ

การแก้สูตรนี้อ่านข้อมูลที่มีอยู่เพื่อคำนวณรายงาน ไม่เขียนแก้ยอดขาย ต้นทุนที่บันทึก สต็อก หรือประวัติธุรกรรมย้อนหลัง ทดสอบกับฐาน in-memory เท่านั้น

### Active POS bill across view switches

The authenticated application shell owns the active cart, quantities (including
special/tier lines), selected member and discount. Switching to inventory,
members or reports and returning to POS keeps that draft without recording a
sale or changing stock. The draft is in memory for the current signed-in shell;
use the existing Hold bill action for storage across a page reload. Logging out
or changing authenticated user starts a separate active draft.

Explicit bill cancellation and successful checkout clear the draft, so a paid
bill cannot reappear as unpaid after leaving the receipt screen. An unchanged
failed/unknown checkout retains its idempotency key across internal navigation.
While checkout is in flight, navigation waits for the result. Payment dialogs
are reopened deliberately rather than carrying a confirmation into another view.

`scripts/pos-navigation-draft-smoke.mjs` uses a fresh demo database to check view
switches, member/discount/quantity retention, cancellation, completed sales,
a lost checkout response retried after navigation, and another user's session.

### จุดขายประจำเบราว์เซอร์

- ป้ายจุดขาย POS แสดงข้อมูลที่ลงทะเบียนจริง ไม่มีเลข 01 หรือสถานะเปิดกะตายตัว
- ผู้บริหารกดป้าย **กำหนดจุดขาย** ใน POS หรือเข้า **ตั้งค่า → เมนูลัดหน้าร้าน → จุดขายของเครื่องนี้** แล้วกำหนดเลข 1–999 ให้เบราว์เซอร์นั้น ระบบกันเลขซ้ำในฐานข้อมูลเดียวกัน
- รหัสสุ่มใน localStorage ใช้จำเบราว์เซอร์ ไม่ใช่ IP, MAC, รหัสผ่าน หรือการยืนยันตัวเครื่องทางฮาร์ดแวร์ หลายแท็บในโปรไฟล์เดียวกันใช้จุดขายเดียวกัน เปลี่ยนเบราว์เซอร์/โปรไฟล์หรือล้างข้อมูลต้องลงทะเบียนใหม่ ผู้บริหารยกเลิกการผูกเครื่องเดิมเพื่อใช้เลขเดิมกับเครื่องใหม่ได้
- หลังอัปเดต ผู้บริหารต้องลงทะเบียนแต่ละเครื่องก่อนชำระเงินครั้งถัดไป หน้าเว็บและ API ไม่ยอมขายด้วยเครื่องที่ยังไม่ลงทะเบียน บัญชีผู้ขายแยกจากจุดขาย
- บิลใหม่เก็บรหัสและเลขจุดขาย ณ เวลาขาย แสดงในใบเสร็จใหม่/พิมพ์ซ้ำ การเปลี่ยนเลขหรือยกเลิกการผูกไม่เปลี่ยนบิลย้อนหลัง บิลเก่าที่ไม่มีจุดขายคงเป็นไม่ระบุ ไม่เดาว่าเป็นจุดขาย 01
- การคืนผลบิลเดิมด้วย clientRequestId ยังคงเลขจุดขายเดิม แม้ยกเลิกการผูกแล้ว ป้องกันชำระซ้ำเมื่อคำตอบจากเซิร์ฟเวอร์สูญหาย การเปิด/ปิดกะยังใช้ระบบกะเดิม ไม่ตีความการลงทะเบียนว่าเปิดให้บริการ
- การอัปเดตฐานข้อมูลเพิ่มตาราง pos_terminals และคอลัมน์ใน sales เท่านั้น ไม่มีการล้างข้อมูลธุรกิจ

ปุ่มรับเข้า: เพิ่มลงรายการและยกเลิกอยู่แถวเดียวกันในกรอบซ้าย ยกเลิกเล็กกว่า ปุ่มบันทึกและคำแนะนำอยู่ในกรอบขวา ทั้งหน้ารับเข้าและหน้าต่างรับเข้าใช้รูปแบบเดียวกัน

### ตรวจเลเอาต์และเอกสารทั้งระบบ

- คงคลังจัดหัวข้อและชุดตัวกรองเป็นแนวเดียวกัน ไม่ดันตัวกรองไปรวมมุมขวา บนมือถือปุ่ม CSV/Excel/PDF/พิมพ์/พรีวิวอยู่ใต้ “ส่งออก / พิมพ์” และแท็บคงคลัง/สั่งซื้อ/รับเข้าเข้าถึงได้ในแถวเดียว
- ช่องค้นหาหน้าต้นทุนและกำไรต้องอยู่ในกรอบบนมือถือ การ์ดสรุปสมาชิกและผู้ใช้ใช้สองคอลัมน์เพื่อให้รายการจริงขึ้นมาเร็วขึ้น
- การค้นหาบิลคงขีดและคำนำหน้าเลขบิล เช่น RC-261023-001 ไม่แปลงเป็นตัวเลขติดกัน รองรับข้อความจาก QR/URL/JSON
- ตัวกรองสมาชิกในประวัติบิลและธุรกรรมแสดงในแถวตัวกรองของตนเอง ไม่แย่งช่องค้นหาหลักจนค้นหาเลขบิลไม่ได้
- หน้าต่างเพิ่ม/แก้ไขผู้ใช้และตั้งรหัสผ่านใช้กรอบ dialog มาตรฐาน รองรับ Escape และกันปิดด้วย Escape ระหว่างบันทึก
- พรีวิว A4 ขยาย iframe ตามความสูงเอกสารจริง ใช้แถบเลื่อนของพรีวิวชุดเดียว รวมถึงเอกสารหลายหน้า ไม่จำกัดกรอบ iframe ไว้แค่หน้าแรก
- เอกสารคงคลังแบ่งความกว้างคอลัมน์รหัสและยอดเงินชัดเจน หัวตารางยาวขึ้นบรรทัดได้โดยไม่เบียดคอลัมน์ข้างเคียง ประวัติรับเข้าลดคอลัมน์ราคา/มูลค่าที่ซ้ำกันจาก 11 เหลือ 9 ทั้งหน้าจอและส่งออก ค่าที่แสดงยังเป็นราคาขายปัจจุบัน ไม่มีการแก้ต้นทุนหรือยอดเงินธุรกิจ
- การตรวจใช้ฐานข้อมูล fixture แยก สินค้า 224 รายการ รวมชื่อยาว รหัสยาว และเอกสารหลายหน้า การจำลองรับงานพิมพ์และ PDF ไม่ยืนยันผลกระดาษจากเครื่องพิมพ์จริง
