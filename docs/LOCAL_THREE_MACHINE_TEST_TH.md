# ทดสอบ Shop ภายในร้าน: เครื่องหลัก 1 เครื่อง และเครื่องใช้งาน 2 เครื่อง

## สถานะของรอบนี้

แยกสัญญาข้อมูลธุรกิจ 78 รายการจาก `server/sqliteStore.ts` ไปที่ `shared/storeTypes/` แบ่งเป็น inventory, members, sales, reports, settings และ access หน้าจออ้างชนิดข้อมูลกลางโดยตรง ใช้ชื่อ Product/Member แทนชื่อที่ผูกกับ SQLite ส่วนเซิร์ฟเวอร์ยังมี compatibility exports สำหรับผู้เรียกเดิม

รอบนี้ไม่เปลี่ยน schema, SQL, สูตรเงิน, สิทธิ์ หรือขั้นตอน commit/rollback และไม่ย้ายข้อมูลจริง ระบบธุรกิจยังใช้ SQLite ยังไม่มี PostgreSQL adapter หรือตัวติดตั้ง Windows จึงยังใช้เอกสารนี้เป็นหลักฐานว่าพร้อมติดตั้งจริงไม่ได้

## เครื่องและเครือข่าย

| เครื่อง | บทบาท | สิ่งที่ต้องเตรียม |
| --- | --- | --- |
| A: เครื่องหลัก Windows | รัน Shop และฐานข้อมูลทดสอบส่วนกลาง | Windows 11 64 บิต, Node.js ที่รองรับ node:sqlite (ใช้ Node 24 LTS สำหรับชุดทดสอบนี้), RAM แนะนำ 16 GB, SSD, จอง IP ที่เราเตอร์, ป้องกัน sleep ระหว่างเปิดร้าน |
| B: หน้าร้าน | POS, สแกนสินค้า, รับชำระ, พิมพ์สลิป | Edge/Chrome, บาร์โค้ดสแกนเนอร์, ไดรเวอร์เครื่องพิมพ์ และ Printer Helper หากใช้พิมพ์ผ่าน Helper |
| C: ออฟฟิศ | รับเข้า สมาชิก รายงาน และงานผู้บริหาร | Edge/Chrome, เครื่องพิมพ์ A4 พร้อมไดรเวอร์/Helper หากต้องการทดสอบพิมพ์ |

ทั้งสามเครื่องอยู่ LAN เดียวกัน เปิดพอร์ตแอปเฉพาะเครือข่าย Private ที่ต้องใช้ ไม่เปิดฐานข้อมูลออกอินเทอร์เน็ต เครื่อง B/C เข้า URL ของเครื่อง A; ห้ามรันสำเนาฐานข้อมูลแยกแล้วคาดหวังว่าจะเห็นข้อมูลร่วมกัน ห้ามนำไฟล์ SQLite ไปเปิดร่วมกันผ่าน network share

ใช้ HTTPS ที่เบราว์เซอร์เชื่อถือสำหรับทดสอบผ่าน LAN โดยเฉพาะกล้องและ session; การเปิดผ่าน IP ด้วย HTTP อาจมีข้อจำกัดที่ localhost ไม่มี ดูขั้นตอนปัจจุบันใน `docs/LOCAL-SETUP.md` และตรวจชื่อไฟล์คู่มือใน repository หากมีการย้ายเอกสาร

## แยกข้อมูลทดสอบ

1. ใช้โฟลเดอร์ข้อมูลและฐานข้อมูลใหม่สำหรับทดสอบเท่านั้น ระบุ `SQLITE_DB_PATH` ให้ชัดเจนตามคู่มือรันปัจจุบัน ไม่ใช้ไฟล์ธุรกิจจริง
2. สร้างผู้ดูแลและบัญชีทดสอบแยกตามบทบาท ใช้รหัสผ่านใหม่ ไม่แจกบัญชีผู้ดูแลให้แคชเชียร์
3. หากต้องทดสอบข้อมูลเดิม ให้ใช้สำเนาสำรองที่ตรวจความสมบูรณ์แล้ว และเก็บสำเนาต้นฉบับไว้อีกแห่ง ลดข้อมูลส่วนบุคคลเท่าที่ทดสอบได้
4. เตรียมสินค้าติดบาร์โค้ด/ไม่มีบาร์โค้ด สินค้าหลาย Lot และสมาชิกทดสอบพร้อมยอดเงินเริ่มต้นที่บันทึกไว้
5. ลงทะเบียนจุดขายเฉพาะเบราว์เซอร์ที่ใช้รับชำระ ให้หมายเลขไม่ซ้ำกัน เครื่องออฟฟิศที่ไม่รับชำระไม่จำเป็นต้องกำหนดจุดขาย

## รายการทดสอบก่อนทดลองหน้างาน

| กรณี | วิธีทดสอบ | ผลที่ต้องได้ |
| --- | --- | --- |
| ข้อมูลกลาง | B ขาย และ C ตรวจสต็อก/รายงานหลังโหลดข้อมูลใหม่ | บิล ยอดเงิน และสต็อกสอดคล้องกัน |
| สินค้าชิ้นสุดท้าย | B/C พยายามขายสินค้าคงเหลือ 1 ชิ้นพร้อมกัน | สำเร็จเพียงรายการเดียว สต็อกไม่ติดลบ |
| เงินสมาชิก | B/C พยายามใช้ยอดเงินก้อนเดียวกันพร้อมกัน | ใช้เกินยอดไม่ได้ ประวัติและยอดคงเหลือตรงกัน |
| ส่งซ้ำ/เครือข่ายสะดุด | ส่งคำขอเดิมซ้ำหลังผลตอบกลับขาดหาย | ไม่สร้างบิลซ้ำ ไม่ตัดเงินหรือตัดสต็อกซ้ำ |
| รับเข้าและขาย | C รับเข้าสินค้าขณะ B ขายสินค้าเดียวกัน | จำนวน Lot/ต้นทุน/ยอดขายตรวจเทียบได้ |
| สิทธิ์ | ใช้บัญชีแคชเชียร์เรียกงานผู้บริหาร | เซิร์ฟเวอร์ปฏิเสธ ไม่อาศัยเพียงการซ่อนปุ่ม |
| งานค้าง | B เปลี่ยนเมนูแล้วกลับ POS | ตะกร้ายังคงอยู่; ปัจจุบันการ refresh/ปิดเบราว์เซอร์ต้องใช้พักบิล ไม่ถือว่ารองรับการกู้ตะกร้าอัตโนมัติ |
| พิมพ์ | B พิมพ์สลิป C พิมพ์รายงานจริง | ออกเครื่องถูกตัว ไม่ตัดคอลัมน์ ขนาดกระดาษถูกต้อง |
| รีสตาร์ต | รีสตาร์ต A แล้วเชื่อมต่อใหม่ | รายการที่บันทึกแล้วอยู่ครบ; การเริ่มบริการอัตโนมัติจะทดสอบซ้ำเมื่อมีตัวติดตั้ง |
| สำรอง/กู้คืน | สำรองแล้วกู้คืนไปโฟลเดอร์ทดสอบอีกชุด | ยอดสมาชิก สต็อก และบิลตรงกัน ไม่เขียนทับฐานที่เปิดใช้งาน |

บันทึกเวอร์ชันแอป Windows เบราว์เซอร์ เครื่องพิมพ์ เวลา และผลผ่าน/ไม่ผ่านทุกกรณี การทดสอบใน cloud ไม่ทดแทนการลองบนสามเครื่องและเครื่องพิมพ์จริง

## ขั้นต่อไป

แยก service/repository และ transaction boundary ก่อนเพิ่ม PostgreSQL adapter จากนั้นทดสอบกรณีข้างต้นบน PostgreSQL แล้วทำ Setup/นำเข้า/Windows service/ตัวติดตั้ง ไม่ใช้ `db:push` เดิมกับ PostgreSQL เพราะเส้นทางนั้นเป็น MySQL OAuth และไม่ใช่ schema ธุรกิจ Shop
