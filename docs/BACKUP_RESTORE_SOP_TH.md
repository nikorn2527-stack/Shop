# SOP: การสำรองและกู้คืนข้อมูล (Backup & Restore)

เอกสารมาตรฐานปฏิบัติงาน (Standard Operating Procedure) สำหรับระบบสำรองและกู้คืนฐานข้อมูล SQLite ของร้านค้าสวัสดิการ ครอบคลุมการสำรองอัตโนมัติ, การเข้ารหัส, การกู้คืน, การทดสอบกู้คืน (restore drill), การตอบโต้เหตุการณ์ ransomware, และ RPO/RTO

> ผู้ใช้: ผู้บริหารระบบ (admin) และผู้พัฒนาระบบ (dev)
> บทบาทในระบบ: admin ทำงานระดับวัน, dev ทำ quarterly restore drill
> เอกสารนี้คู่กับ `docs/sqlite-backup.md` (รายละเอียดเชิงเทคนิค CLI) และโค้ดใน `server/sqliteBackup.ts`

---

## 1. นโยบายการสำรองข้อมูล (Backup Policy)

- **สำรองอัตโนมัติทุก 24 ชั่วโมง** — ระบบสำรองฐานข้อมูล `welfare-store.sqlite` เป็นไฟล์ timestamped ในรูป `welfare-store-YYYYMMDDTHHMMSSZ.sqlite` (หรือ `.sqlite.enc` เมื่อเปิดเข้ารหัส) ภายใต้โฟลเดอร์ `data/backups/`
- **สำรองด้วยตนเองเมื่อจำเป็น** — ผู้บริหารสามารถกดสำรองเดี๋ยวนี้ได้ที่ **แท็บสำรองข้อมูล** ในหน้าตั้งค่าระบบ → ปุ่ม "สำรองข้อมูล" — เหมาะก่อนทำงานใหญ่ (อัปเดตเวอร์ชัน, นำเข้าข้อมูลจำนวนมาก, ปิดยอดประจำวัน)
- **ก่อนเปลี่ยนแปลงใหญ่ทุกครั้ง** (ล้างข้อมูล, ย้ายร้าน, อัปเกรดสคีมา) — ต้องสำรองเองก่อนเสมอ ไม่ฝาก cron อย่างเดียว
- **ไฟล์สำรองไม่ commit เข้า Git** — โฟลเดอร์ `data/backups/` ถูก `.gitignore` ไว้ และควรคัดลอกไปยัง storage คนละเครื่อง (เช่น external drive, object storage ที่มี versioning) เป็นระยะ

## 2. นโยบายการเก็บรักษา (Retention Policy)

- **เก็บไฟล์สำรองล่าสุด 14 ไฟล์** (ค่า default `backupKeepCount = 14` ในตาราง `store_settings`) — `pruneSqliteBackupsByCount` ลบไฟล์เก่ากว่า 14 ลำดับอัตโนมัติทุกครั้งที่สำรองใหม่
- **เก็บไม่เกิน 30 วัน** — ไฟล์ที่เก่ากว่า 30 วันตาม mtime จะถูกลบโดย `pruneSqliteBackups` (รันจาก cron รายวัน)
- **การตั้งค่า** — ผู้บริหารปรับ `backupKeepCount` และ `backupAutoEnabled`, `backupIntervalHours` ได้ที่แท็บตั้งค่าระบบ → สำรองข้อมูล (เวอร์ชันโปรขึ้นไป)
- **ไฟล์ manifest (.json)** — ทุกไฟล์สำรองมี sidecar `<file>.json` เก็บ sha256, sizeBytes, createdAt, encrypted — ถ้า manifest หาย รายการยังแสดงได้แต่ integrity = "unknown"

## 3. ขั้นตอนการกู้คืนข้อมูล (Restore Procedure)

> ใช้เมื่อ: ฐานข้อมูลเสีย, ลบข้อมูลผิด, ย้ายข้อมูลข้ามเครื่อง, หรือหลังเหตุการณ์ ransomware
> ผู้ทำ: ผู้บริหาร (admin) เท่านั้น — ระบบบังคับสิทธิ์ admin และสำรองไฟล์ป้องกันก่อนกู้คืนเสมอ

1. **เข้าสู่ระบบในฐานะผู้บริหาร** — เปิดเว็บแอป → ลงชื่อเข้าใช้ด้วยบัญชีผู้บริหาร
2. **เปิดแท็บสำรองข้อมูล** — ไปที่หน้าตั้งค่าระบบ → แท็บ "สำรองข้อมูล" (เวอร์ชันโปรขึ้นไป)
3. **เลือกไฟล์สำรองที่จะกู้คืน** — ดูรายการไฟล์สำรอง (เรียงใหม่สุดก่อน) และเลือกไฟล์ที่ต้องการ — ดู createdAt, sizeBytes, integrity ("ok" = ผ่าน integrity check)
4. **แนะนำให้ทดสอบกู้คืนก่อน** (optional แต่แนะนำ) — กดปุ่ม "ทดสอบกู้คืน" บนไฟล์นั้นเพื่อยืนยันว่าไฟล์เปิดได้, integrity ผ่าน, และมีตารางที่คาดไว้ (ดูรายละเอียดใน §4)
5. **กดปุ่ม "กู้คืน"** บนไฟล์ที่เลือก → ยืนยันใน dialog
6. **ระบบทำงานอัตโนมัติ:**
   - สำรองไฟล์ป้องกัน (safety backup) ของฐานข้อมูลปัจจุบันก่อนเสมอ — ถ้ากู้คืนพลาด ยังมีไฟล์กลับรอ
   - ปิด handle เดิม, ลบไฟล์ `welfare-store.sqlite` + `-wal` + `-shm`
   - คัดลอกไฟล์สำรองทับตำแหน่งเดิม (decrypt ก่อนถ้าไฟล์ `.enc`) — ตรวจ `PRAGMA integrity_check` อีกครั้งหลังเขียนเสร็จ
   - เปิดฐานข้อมูลใหม่ (lazy) — บันทึก audit log สีแดง "กู้คืนข้อมูล"
7. **ยืนยันผล** — กลับไปหน้า dashboard / รายการสมาชิก / สต็อกสินค้า เพื่อเช็คว่าข้อมูลกลับมาเป็นไฟล์สำรองที่เลือก
8. **บันทึกเหตุการณ์** — ผู้บริหารบันทึกเวลา, ไฟล์ที่กู้คืน, เหตุผล และผู้อนุมัติ ลงใน log ภายนอกระบบ (เช่น spreadsheet รายการเหตุการณ์สำคัญ) — ระบบบันทึก audit log อัตโนมัติอยู่แล้ว

> ⚠️ คำเตือน: ข้อมูลหลังจุดสำรองล่าสุดจะหายไป (RPO = 24 ชม. — ดู §7) — ถ้ามีธุรกรรมใหม่หลัง backup ล่าสุด ข้อมูลเหล่านั้นจะไม่กลับคืน

## 4. ขั้นตอนทดสอบกู้คืน (Restore Drill Procedure)

> ใช้เมื่อ: ต้องการยืนยันไฟล์สำรองใช้งานได้โดยไม่กระทบฐานข้อมูลจริง
> ผู้ทำ: ผู้บริหารทำได้ทุกเมื่อ, ผู้พัฒนาทำ quarterly drill ตามนโยบาย §8

1. **เข้าสู่ระบบในฐานะผู้บริหาร**
2. **เปิดแท็บสำรองข้อมูล** — หน้าตั้งค่าระบบ → แท็บ "สำรองข้อมูล"
3. **เลือกไฟล์สำรอง** ที่ต้องการทดสอบ และกดปุ่ม **"ทดสอบกู้คืน"** (procedure `backup.testRestore`)
4. **ระบบทำงานอัตโนมัติ (ไม่แตะฐานข้อมูลจริง):**
   - ถอดรหัส (decrypt) ไฟล์ `.sqlite.enc` ไปยัง temp file (ถ้าเข้ารหัส)
   - เปิด temp read-only → รัน `PRAGMA integrity_check`
   - รายชื่อตารางทั้งหมด (`SELECT name FROM sqlite_master WHERE type='table'`)
   - นับแถวในตารางหลัก: `products`, `members`, `sales`, `sale_items`
   - ลบ temp file
5. **ระบบคืนผลลัพธ์:** `{ ok: true, tables: string[], rowCount: number }` พร้อมบันทึก audit log สีฟ้า "ทดสอบกู้คืน"
6. **ตีความผล:**
   - `ok: true` + `integrity_check = "ok"` → ไฟล์สำรองสมบูรณ์, ใช้กู้คืนได้
   - รายชื่อตารางครบ (มีอย่างน้อย `app_users`, `members`, `products`, `store_settings`) → เป็นฐานข้อมูลของระบบร้านค้าสวัสดิการจริง (ไม่ใช่ SQLite ของโปรแกรมอื่น)
   - `rowCount` สมเหตุผล (ไม่ตัว 0 ทั้งหมด) → ข้อมูลอยู่ในไฟล์สำรอง
   - ถ้า procedure throw "Failed to decrypt backup (wrong key ...)" → คีย์เข้ารหัสไม่ตรงกับที่ใช้สำรอง — หาคีย์เดิมก่อน

## 5. การตั้งค่าการเข้ารหัส (Encryption Setup)

> ค่าเริ่มต้น: ปิดอยู่ (backward compatible — ไฟล์สำรองเป็น plain `.sqlite` เหมือนเดิม)
> เปิดใช้: ตั้ง `BACKUP_ENCRYPTION_KEY` ใน `.env` — สำรองใหม่ทุกไฟล์จะเข้ารหัส AES-256-GCM อัตโนมัติ

### วิธีเปิดใช้งาน

1. สร้างคีย์สุ่มอย่างน้อย 32 ตัวอักษร — แนะนำให้ใช้:
   ```bash
   openssl rand -base64 32
   ```
2. ตั้งใน `.env` ของเซิร์ฟเวอร์:
   ```env
   BACKUP_ENCRYPTION_KEY=<paste-key-here>
   ```
3. รีสตาร์ทเซิร์ฟเวอร์ — สำรองใหม่ทุกไฟล์จะถูกเข้ารหัสอัตโนมัติ (นามสกุล `.sqlite.enc`)
4. **ทดสอบ** — สำรองเอง 1 ไฟล์ → กด "ทดสอบกู้คืน" → ต้องได้ `ok: true` และรายชื่อตารางครบ

### รายละเอียดเทคนิค

- **Algorithm**: AES-256-GCM (authenticated encryption — ตรวจจับการดัดแปลงได้)
- **Key derivation**: `crypto.scryptSync(password, salt="png-shop-backup-salt", keylen=32)` — ป้องกัน brute force
- **File layout**: `[12-byte IV][16-byte auth tag][ciphertext]` — IV สุ่มทุกไฟล์
- **Manifest flag**: `encrypted: true` ใน `<file>.json` sidecar — แต่ restore ใช้สกุลไฟล์ `.enc` auto-detect ไม่ต้องพึ่ง manifest
- **Plain file cleanup**: หลังเข้ารหัสเสร็จ ระบบลบ plain `.sqlite` ออกจาก disk ทันที — เหลือเฉพาะ `.sqlite.enc`

### ข้อควรระวัง

- **ถ้าคีย์หาย** — ไฟล์ `.sqlite.enc` ทั้งหมดที่เข้ารหัสด้วยคีย์นั้นกู้คืนไม่ได้ — เก็บคีย์ไว้ใน password manager / secrets vault อย่างน้อย 2 สำเนา
- **ถ้าเปลี่ยนคีย์** — ไฟล์เก่าที่เข้ารหัสด้วยคีย์เดิมจะถอดรหัสไม่ได้ — สำรองใหม่ด้วยคีย์ใหม่ก่อน แล้วค่อยลบไฟล์เก่า
- **โหลดไม่ได้ถ้าไม่ตั้งคีย์** — ถ้าตั้ง `BACKUP_ENCRYPTION_KEY` ครั้งเดียวแล้วลบ env var ภายหลัง ระบบจะกู้คืนไฟล์ `.sqlite.enc` ไม่ได้ — ตั้งคีย์ครั้งเดียวแล้วอย่าลบ
- **โหลดไม่ได้ถ้าสั้นเกิน** — `BACKUP_ENCRYPTION_KEY` ต้องยาว ≥ 32 ตัวอักษร — ถ้าสั้นกว่านี้ระบบ treat เป็น "ปิดเข้ารหัส" และสำรองเป็น plain `.sqlite`

## 6. การตอบโต้เหตุการณ์ Ransomware (Ransomware Response)

> ใช้เมื่อ: สงสัยว่าระบบโดน ransomware หรือ malware เข้ารหัสไฟล์, ไฟล์สำรองถูกดัดแปลง, หรือพบพฤติกรรมผิดปกติ

### ขั้นตอนเร่งด่วน (ทำทันทีที่สงสัย)

1. **ตัดการเชื่อมต่อเครือข่าย** — ถอดสาย LAN/Wi-Fi หรือ disable network interface ทันที — ป้องกันการกระจายตัวของ ransomware ไปเครื่องอื่นและการเข้ารหัสไฟล์เพิ่ม
2. **หยุดเซิร์ฟเวอร์** — `Ctrl+C` หรือ `systemctl stop` กระบวนการ Node.js ที่เปิดฐานข้อมูลอยู่ — ป้องกันการเขียนทับไฟล์สำรองที่ยังดี
3. **อย่าจ่ายไหว้** — ไม่จ่ายค่าไถ่ — ระบบสำรองข้อมูลของเราออกแบบให้กู้คืนได้โดยไม่ต้องจ่าย

### ขั้นตอนกู้คืน (หลักตัดเครือข่าย)

4. **ตรวจสอบไฟล์สำรอง** — บนเครื่องคัดลอก (external drive / object storage) เช็คว่า:
   - ไฟล์สำรองล่าสุดยังไม่ถูกเข้ารหัส (สกุลยังเป็น `.sqlite.enc` หรือ `.sqlite` ตามปกติ)
   - ขนาดไฟล์, sha256 ตรงกับ manifest — ถ้าไม่ตรง แปลว่าไฟล์โดนดัดแปลง
5. **ทดสอบกู้คืนบนเครื่องที่สะอาด** — คัดลอกไฟล์สำรองไปเครื่องที่ไม่ได้ติด ransomware → รัน restore drill (`backup.testRestore` หรือ `pnpm backup:sqlite:verify <file>`) → ยืนยัน `integrity_check = "ok"` ก่อน
6. **กู้คืนจากไฟล์สำรองล่าสุดที่สะอาด** — ทำตาม §3 ขั้นตอนปกติ — ระบบสำรองไฟล์ป้องกันก่อนกู้คืนอยู่แล้ว (safety backup)
7. **ถ้าเปิดเข้ารหัส (`BACKUP_ENCRYPTION_KEY`)** — ไฟล์ `.sqlite.enc` จะไร้ประโยชน์กับผู้โจมตีแม้ขโมยไปได้ — ตราบใดที่คีย์ยังไม่รั่ว

### ขั้นตอนหลังกู้คืน (Post-Incident)

8. **ตรวจ audit logs** — เปิดหน้า logs (ผู้บริหาร → แท็บประวัติการทำงาน) — ดูกิจกรรมผิดปกติช่วงก่อนเหตุการณ์: การเข้าสู่ระบบต่างปกติ, การกู้คืนข้อมูลที่ไม่ได้รับอนุญาต, การเปลี่ยนสิทธิ์, การสร้าง/ลบบัญชี
9. **เปลี่ยนรหัสผ่านทั้งหมด** — รหัสผ่านผู้บริหาร, ผู้ใช้งานทุกคน, และคีย์เข้ารหัส (`BACKUP_ENCRYPTION_KEY`) ทันที — สมมติว่าผู้โจมตีได้ข้อมูลการเข้าถึงไปแล้ว
10. **อัปเดตและสแกน** — อัปเดตระบบปฏิบัติการ, ติดตั้ง antivirus, สแกนเครื่องทุกเครื่องที่เชื่อมเครือข่าย
11. **บันทึกเหตุการณ์** — ผู้พัฒนาเขียน post-mortem: timeline, root cause, ไฟล์สำรองที่ใช้กู้คืน, ข้อมูลที่สูญหาย (ระหว่าง RPO), มาตรการป้องกัน

## 7. RPO / RTO

| ตัวชี้วัด | เป้าหมาย | ความหมาย | วิธีทำให้ได้ |
|----------|----------|----------|-------------|
| **RPO** (Recovery Point Objective) | **24 ชั่วโมง** | ข้อมูลที่อาจสูญหายสูงสุด = 24 ชม. ย้อนหลัง | สำรองอัตโนมัติทุก 24 ชม. (cron) + ผู้บริหารสำรองเองก่อนงานใหญ่ |
| **RTO** (Recovery Time Objective) | **15 นาที** | เวลาที่ระบบกลับมาใช้งานได้หลังเหตุการณ์ = 15 นาที | ทดสอบกู้คืน (§4) ทำให้รู้ว่าไฟล์สำรองใช้ได้ก่อน → กดกู้คืน (§3) → ระบบทำ safety backup + copy + verify อัตโนมัติ |

> การทำ quarterly restore drill (§8) คือวิธีรักษา RTO 15 นาที — ถ้าไม่ซ้อม ผู้บริหารจะเสียเวลาตื่นตระหนก หาปุ่มผิด ตอนเหตุการณ์จริง

## 8. ความรับผิดชอบ (Responsibility Matrix)

| บทบาท | งานประจำวัน | งานรายไตรมาส (Quarterly) | งานตอนเหตุการณ์ |
|------|------------|--------------------------|------------------|
| **ผู้บริหาร (admin)** | ดูแอปแจ้งเตือน cron สำรองรายวัน, สำรองเองก่อนงานใหญ่, ตอบโจมตี ransomware ขั้นที่ 1-2 (ตัดเครือข่าย, เรียก dev) | — | ตัดเครือข่าย, หยุดเซิร์ฟเวอร์, เรียกผู้พัฒนา, กู้คืนตามคำแนะนำ |
