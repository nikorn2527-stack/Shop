## งานสำคัญที่ยังเปิดอยู่

1. **ตรวจข้อมูลการชำระที่ API — แก้แล้วในชุดต่อเนื่อง:** ดูรายละเอียดด้านล่าง การยืนยัน QR เป็นการยืนยันของแคชเชียร์ ยังไม่ใช่การตรวจยอดโอนกับธนาคารอัตโนมัติ
2. **ยกเลิกบิลข้ามรอบ — เพิ่มตัวป้องกันแล้ว:** ปฏิเสธการ void นอกรอบปัจจุบันหรือบิลที่รวมในรอบที่ปิดแล้ว โดยไม่เปลี่ยนเงิน/สต็อก รายการคืนเงินข้ามรอบแบบมีเอกสารปรับปรุงยังไม่ได้พัฒนา
3. **Idempotency ของ POS — เพิ่ม fingerprint และ snapshot แล้ว:** คำขอเดิมคืนบิลเดิม; key เดิมแต่ข้อมูลเปลี่ยน/บิลยกเลิก/ไม่มี fingerprint เดิมถูกปฏิเสธ wallet API ได้เพิ่มการตรวจแบบเดียวกันแล้วในชุดเงินสมาชิกด้านล่าง
4. **PostgreSQL จริงและ LAN:** มีโครงสร้าง async/transaction เบื้องต้น แต่ยังไม่มี driver/schema migration/runtime PostgreSQL ที่ใช้งานจริง การทดสอบ Windows หลักหนึ่งเครื่องกับ client อีกสองเครื่อง รวม concurrency, restart, backup/restore, firewall และสิทธิ์ผู้ใช้ยังต้องทำ

## ชุดต่อเนื่อง: ความถูกต้องของข้อมูลชำระเงิน

- Public checkout API บังคับยอดรับเงินสด และบังคับ paymentVerified=true สำหรับ QR; จำนวนเงิน NaN/Infinity ถูกปฏิเสธตาม schema
- Checkout service ตรวจยอดรับเงินสดที่ให้มาต้องเพียงพอและเป็นจำนวนจำกัด และคำนวณเงินทอนจากยอดสุทธิเอง ไม่เชื่อ changeDue ที่ client ส่งมา ผลบันทึก/receipt/replay ใช้เงินทอนจาก server เหมือนกัน
- สินค้าปกติใช้ราคาขาย ชื่อ และหน่วยจาก catalog; ปฏิเสธ price override ที่ไม่ตรงและสินค้าที่ยังไม่ตั้งราคา
- สินค้าขายเป็นเงินเลือกได้เฉพาะ label/ราคาต่อหน่วย/จำนวนที่ตรงกับ priceTiers ในฐานข้อมูล จำนวนต้องเป็นจำนวนเต็มของ portion; ใช้ราคาต่อ portion คำนวณยอดจริงเพื่อไม่ให้คลาดเคลื่อนจากการปัดราคาต่อหน่วยสี่ตำแหน่ง เช่น 10 บาทต่อ 3 กรัม จำนวน 6 กรัมคิด 20 บาท
- ตรวจ POS.DISCOUNT และ POS.SPECIAL เพิ่มตามสิทธิ์จริงที่ยังมีอยู่ พร้อม edition gate เดิมของรายการพิเศษ
- API ไม่ถูกแทนที่ด้วย service ภายใน: legacy internal callers ที่ไม่ผ่าน public API ยังละยอดรับเงินสด/confirmation ได้เพื่อรองรับ call sites เดิม การบังคับ presence/QR confirmation อยู่ที่ public route; การคิดราคาและเงินทอนอยู่ที่ service ภายใน transaction

เพิ่ม checkout.integrity.test.ts 23 tests: ค่ารับเงินสดหาย/ไม่ถูกต้อง/ไม่พอ, QR ไม่ยืนยัน, ปลอมราคา/หน่วย, ช่วงราคาที่ถูกต้อง/ไม่ถูกต้อง, จำนวน portion, สินค้ายังไม่ตั้งราคา, สิทธิ์ส่วนลด/รายการพิเศษถูกถอน, และ replay ไม่ตัดสต็อกซ้ำ ชุดเฉพาะ checkout/terminal/permissions/atomicity ผ่าน 4 ไฟล์ / 63 tests

ข้อจำกัดคงเดิม: การโอนเงินจริงยังอาศัยแคชเชียร์ตรวจสอบ ไม่มี bank integration; key ซ้ำยังไม่ตรวจ payload fingerprint; การยกเลิกบิลข้ามรอบยังต้องออกแบบรายการปรับปรุงและรายงานก่อนใช้งานจริง

ผลตรวจชุดชำระเงินก่อนชุด retry/รอบขาย: TypeScript ผ่าน, production build ผ่าน และ automated suite ผ่าน 66 ไฟล์ / 524 tests โดยใช้ฐานข้อมูลทดสอบแยก ไม่เปลี่ยน schema/dependency หรือข้อมูลธุรกิจ

## ชุดต่อเนื่อง: คำขอซ้ำและขอบเขตรอบขาย

### POS retry

ทุก public checkout ต้องมี clientRequestId ที่ไม่ว่าง หน้าขายปัจจุบันสร้าง UUID ต่อการชำระหนึ่งครั้งและส่งซ้ำเมื่อ retry อยู่แล้ว จึงไม่เพิ่มขั้นตอนให้แคชเชียร์ Internal legacy callers ยังละ key ได้ตามเดิม และไม่ได้รับการป้องกัน retry เมื่อไม่ส่ง key

ระบบเก็บ SHA-256 ของ payload แบบมี version โดยรวมสินค้า/จำนวน/ราคาและช่วงราคาที่ส่งมา ส่วนลด สมาชิก วิธีจ่าย ยอดรับเงินสด การยืนยัน QR หลักฐานการจ่าย จุดขาย และตัวตนผู้ขายจากเซสชัน ไม่รวมเงินทอนหรือหน่วย catalog ที่ server คำนวณเอง

- key และข้อมูลตรงกัน: คืน receipt snapshot เดิม โดยไม่ตรวจราคา/สต็อก/สมาชิกปัจจุบันใหม่และไม่ตัดเงินซ้ำ ทดสอบปิดเปิดฐานข้อมูลจำลองใหม่ รวมเปลี่ยนชื่อสมาชิก/ราคาและยกเลิกผูกจุดขาย
- key เดิมแต่ข้อมูลเปลี่ยน: ปฏิเสธพร้อมเลขบิลเดิมให้ตรวจสอบ ไม่สร้างบิลใหม่
- บิลยกเลิกแล้ว: ปฏิเสธ ไม่ส่ง receipt เก่ากลับเป็นการชำระสำเร็จ
- บิลรุ่นเก่าที่มี key แต่ไม่มี fingerprint: ปฏิเสธ retry พร้อมบอกให้ตรวจประวัติบิล ไม่คาดเดาว่าคำขอเดิมตรงกัน และไม่ตัดเงินซ้ำ
- snapshot ถูกบันทึกใน transaction เดียวกับเงิน สต็อก และ audit หากเขียน snapshot ไม่สำเร็จ rollback ทั้งหมด

### รอบขาย

void ทำได้เฉพาะบิลในรอบปัจจุบันที่ยังไม่รวมในการตัดยอด บิลข้ามรอบหรือปิดยอดแล้วได้รับข้อผิดพลาดที่อ่านได้ ไม่มีการคืนสต็อก คืนเงิน หรือแก้รายงานย้อนหลัง นี่เป็นตัวป้องกันชั่วคราว ไม่ใช่ฟังก์ชันคืนสินค้าข้ามรอบ ผู้บริหารยังไม่มีทาง override ตัวป้องกันนี้ผ่าน API

เพิ่ม row cursor ของ sales และ member_transactions ที่การปิดรอบแบบ manual เพื่อแยกรายการก่อน/หลังตัดยอดที่เกิดในวินาทีเดียวกัน ไม่ให้รอบถัดไปนับยอดเก่าใหม่ การปิดรอบอัตโนมัติคงช่วง [เริ่ม, สิ้นสุด) และรายการ ณ เวลาตัดยอดอยู่รอบใหม่ รวมทดสอบ insertion order ที่ไม่เรียงตามเวลา

ข้อมูลรอบเก่าที่ไม่มี cursor ไม่สามารถย้อนรู้ลำดับภายในวินาทีได้แน่นอน ระบบไม่ backfill ด้วยการเดา; การ void ณ วินาทีเดียวกับ closure รุ่นเก่าจะปฏิเสธแบบระมัดระวัง รายงาน legacy ณ boundary นี้ต้องตรวจเทียบเอกสารเดิม ไม่ได้อ้างว่าแก้ตัวเลขย้อนหลังแล้ว

### ยอดบรรทัดสินค้าและ schema

พบระหว่างตรวจ retry ว่ารายการขายแบบ portion ต้องเก็บยอดบรรทัดจริงด้วย เพื่อให้ยอด 10 บาทต่อ 300 หน่วยไม่กลายเป็น 9.99 บาทจากการคูณราคาต่อหน่วยที่ปัดสี่ตำแหน่ง รายการใหม่เก็บ amount ที่ server คำนวณ และ history/report อ่านค่านี้; รายการเก่าที่ amount เป็น NULL ใช้การคำนวณเดิมโดยไม่แก้ข้อมูลย้อนหลัง

เพิ่ม nullable columns เท่านั้นผ่าน migration เดิมตอนเปิดฐานข้อมูล: sales.request_fingerprint, sales.receipt_snapshot, sale_items.amount, day_closures.last_sale_id, day_closures.last_member_tx_id ไม่ลบตาราง/แถว ไม่ backfill ตัวเลขหรือ metadata บิลเก่า ทดสอบจำลองไฟล์รุ่นเก่าโดยไม่มีห้าคอลัมน์นี้แล้วเปิดใหม่ ตรวจเงิน สมาชิก สินค้า และบิลยังอยู่ครบ รอบนี้ไม่เปิดหรือ migrate ไฟล์ธุรกิจจริง การอัปเดตเครื่องใช้งานจริงต้องสำรองและตรวจ restore กับสำเนาก่อน

ข้อจำกัด ณ ชุด POS: wallet API ตรวจต่อในชุดเงินสมาชิกด้านล่าง; ยังไม่มี workflow คืนเงินข้ามรอบ, ไม่มี bank verification และยังไม่ทดสอบ PostgreSQL/Windows LAN/เครื่องพิมพ์จริง

ผลตรวจชุด retry/รอบขายล่าสุด: TypeScript และ production build ผ่าน; automated suite ผ่าน 68 ไฟล์ / 550 tests บนฐานข้อมูลแยก รวมทดสอบ upgrade ไฟล์รุ่นเก่า, snapshot failure rollback, replay หลัง restart และ boundary ในวินาทีเดียวกัน ไม่มีการเปิดหรือเปลี่ยนฐานข้อมูลธุรกิจจริง

## ชุดต่อเนื่อง: คำขอซ้ำของเงินสมาชิก

member.wallet API บังคับ clientRequestId ที่ไม่ว่างสำหรับฝาก ถอน และคืนเงิน หน้าร้านและหน้าสมาชิกมี UUID ต่อคำขออยู่แล้ว จึงไม่เพิ่มการกรอกข้อมูลให้ผู้ใช้ รับตัวตนผู้ทำรายการจากเซสชัน ไม่ใช้ชื่อ/ID ที่ client ส่งเพื่ออ้างตัวผู้ทำรายการ

เก็บ fingerprint รวมสมาชิก ประเภทการเงิน จำนวนเงินหลังปัดสตางค์ หมายเหตุ หลักฐาน ตัวตนผู้ทำรายการ และ flag คืนเงินโดยเก็บบัตรไว้ พร้อม receipt snapshot ในแถว ledger ภายใน transaction เดียวกับยอดเงิน การคืนบัตร และ audit

- คำขอเดิมคืนใบรายการเดิม แม้ restart, เปลี่ยนชื่อ/ยอดสมาชิก หรือคืนเงินครบและนำบัตรไปให้ผู้ถือใหม่แล้ว ไม่เขียน ledger/audit หรือแตะบัตรผู้ถือใหม่
- key เดิมแต่เปลี่ยนสมาชิก จำนวนเงิน ประเภทการเงิน หมายเหตุ ตัวตนเจ้าหน้าที่ หรือเงื่อนไขคืนบัตร ถูกปฏิเสธก่อนเปลี่ยนเงิน
- key รุ่นเก่าที่ไม่มี fingerprint ถูกปฏิเสธพร้อมให้ตรวจประวัติ ไม่ใช้ยอดคงเหลือปัจจุบันคาดเดาใบรายการเก่า
- ถ้าบันทึก snapshot หรือขั้นตอนคืนบัตร/audit ล้มเหลว transaction rollback ทั้งหมด ทดสอบฉีดข้อผิดพลาดรวมกับชุด atomicity เดิม
- ตรวจจำนวนเงินใน service ให้เป็น finite มากกว่า 0 และหลังปัดไม่ต่ำกว่า 0.01 บาท อยู่ในขอบเขตสตางค์ที่ JavaScript แทนค่าได้อย่างปลอดภัย
- API คืนบัตร card.return ต้องมี MEMBER.WALLET เพิ่มเติมจาก login ป้องกัน auditor/stock officer เรียกคืนเงินผ่านอีกเส้นทาง
- ปิดรอบบัญชีด้วย key ของรายการเงินอื่นจะถูกปฏิเสธ ไม่ปิดบัญชีโดยเข้าใจผิดว่าจ่ายเงินคืนแล้ว

เพิ่ม nullable member_transactions.request_fingerprint และ receipt_snapshot ผ่าน migration เดิม พร้อมรักษาฟิลด์เหล่านี้เมื่อ migration รุ่นเก่าต้อง rebuild CHECK constraint ทดสอบเปิดไฟล์ fixture ที่ไม่มีคอลัมน์ใหม่แล้วเพิ่มคอลัมน์ โดยสมาชิก ยอดเงิน และ ledger เดิมยังครบ ไม่มีการแตะไฟล์ธุรกิจจริงหรือ backfill fingerprint เดาเอง

เส้นทาง async ใช้กติกา fingerprint/snapshot เดียวกันและทดสอบการ await/rollback ผ่าน repository doubles เส้นทางนี้ยังไม่ได้ต่อ production router หรือ PostgreSQL จริง

ขอบเขต: public member.wallet บังคับ key; internal legacy calls ยังละ key ได้ เส้นทางรวม card.return/closeAccount ยังใช้การตรวจผู้ถือและรอบบัตรเดิมที่ระดับนอก จึงไม่ได้รับรองว่าการ retry ทั้ง workflow จะได้ผลหน้าจอเดิมทุกครั้งหลังบัตรเปลี่ยนผู้ถือ แม้คำขอ wallet ภายในที่มี key จะไม่จ่ายซ้ำ งานคืนเงินข้ามรอบและการทดสอบ Windows/PostgreSQL/LAN/เครื่องพิมพ์จริงยังคงเหลือ
