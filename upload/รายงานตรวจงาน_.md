# รายงานตรวจงาน `main-v2`

วันที่ตรวจสอบ: 3 ตุลาคม 2569  
Repository: `nikorn2527-stack/Shop`  
Branch: `main-v2`  
Commit ล่าสุดที่ตรวจ: `48e3fe1 fix: sticky footer pattern — main-shell flex column + footer margin-top auto`

## สรุปผล

งานที่ทีมเดิมแก้มา **ยังไม่ตรงกับพฤติกรรมที่ผู้ใช้ต้องการ** ใน 2 กลุ่มหลัก:

1. **Export รายงาน:** CSV และ Excel มีเส้นทางดาวน์โหลดจริง แต่ปุ่ม PDF ในหน้ารายงานยังเปิดหน้าต่างพิมพ์ แล้วให้ผู้ใช้เลือก “บันทึกเป็น PDF” เอง ไม่ใช่การดาวน์โหลด PDF ตรงตามชื่อปุ่ม
2. **บัตรสมาชิก:** ปุ่ม “ดาวน์โหลด PDF” และ “พิมพ์บัตรสมาชิก” เรียก `window.print()` เหมือนกันทุกประการ จึงไม่ใช่คนละการทำงาน และรูปแบบที่พรีวิวกับ output ยังไม่ถูกล็อกด้วยมาตรฐานเดียวกัน

นอกจากนี้ branch นี้มี **ปัญหา build/install ระดับ P0**: `package.json` มี `@phosphor-icons/react` แต่ `pnpm-lock.yaml` ไม่มี dependency/specifier นี้ ทำให้ `pnpm install --frozen-lockfile` ล้มเหลว และใน workspace ที่ตรวจ `pnpm check` พบ module หาย 138 errors

## หลักฐานจากโค้ด

### 1. Export PDF รายงานยังไม่ใช่การดาวน์โหลดไฟล์

ไฟล์ `client/src/pages/reports/Reports.tsx` บรรทัด 1612–1616:

```ts
} else if (format === "pdf") {
  printReportDoc(state.doc);
  setNotice(`เปิดหน้าต่างบันทึก... PDF แล้ว ...`);
}
```

แต่ใน `client/src/reportDoc.ts` มีฟังก์ชันดาวน์โหลดจริงอยู่แล้วที่บรรทัด 130–202:

```ts
export async function downloadReportPdf(config: ReportDocConfig) { ... pdf.save(...) }
```

ดังนั้นปุ่ม PDF ของหน้า Reports **ไม่ได้เรียก `downloadReportPdf()`** แต่เรียก `printReportDoc()` ซึ่งใช้ iframe และ `window.print()` ที่บรรทัด 209 เป็นต้นไป

ผลกระทบ:

- ผู้ใช้ต้องเลือกเครื่องพิมพ์/Save as PDF เอง
- ชื่อไฟล์และตำแหน่งบันทึกขึ้นกับ browser/ระบบปฏิบัติการ
- ปุ่ม PDF กับปุ่มพิมพ์มีพฤติกรรมใกล้เคียงกันเกินไป
- การบอกว่า “ดาวน์โหลด PDF” ไม่ตรงกับสิ่งที่เกิดขึ้นจริง

### 2. ตัว PDF ที่ดาวน์โหลดจริงยังเป็น raster ไม่ใช่ vector เต็มรูปแบบ

`downloadReportPdf()` ใช้ `html2canvas()` ที่บรรทัด 184 แล้วนำ canvas ไปใส่ใน jsPDF ที่บรรทัด 196:

```ts
const canvas = await html2canvas(page, { scale: 2.5, backgroundColor: "#ffffff" });
pdf.addImage(canvas.toDataURL("image/jpeg", 0.95), "JPEG", ...);
```

จึงยังเป็นภาพ JPEG ฝังใน PDF ไม่ใช่ข้อความ/เส้นตารางแบบ vector จริง หากผู้ใช้ซูมมากหรือพิมพ์จาก PDF ความคมอาจไม่เท่ากับเอกสารที่สร้างด้วย text/vector โดยตรง

หมายเหตุ: `printReportDoc()` ให้ตัวอักษร/ตารางคมกว่าในกรณี browser พิมพ์ แต่ยังไม่ใช่ไฟล์ PDF ที่ดาวน์โหลดตรงจากแอป

### 3. บัตรสมาชิกมีปุ่ม 2 ปุ่มแต่ทำงานเหมือนกัน

ไฟล์ `client/src/components/MemberCardModal.tsx` บรรทัด 166–172:

```ts
const downloadCard = () => { window.print(); };
const printCard = () => { window.print(); };
```

ผลคือ:

- “ดาวน์โหลด PDF” ไม่ได้สร้างหรือดาวน์โหลดไฟล์โดยตรง
- “พิมพ์บัตรสมาชิก” และ “ดาวน์โหลด PDF” เปิด print dialog เหมือนกัน
- ยังต้องอาศัยผู้ใช้เลือก “Save as PDF” เองสำหรับการดาวน์โหลด
- ผู้ใช้จึงเห็น output ที่แตกต่างได้ตาม browser, scale, margin และการตั้งค่าเครื่องพิมพ์

### 4. ขนาดบัตรพิมพ์ถูกกำหนดซ้ำและมี rule ขัดกัน

กฎหลักที่ `client/src/index.css` บรรทัด 986 กำหนดถูกต้องเป็น 90×55 มม.:

```css
.member-card { width: 90mm; height: 55mm; }
```

แต่กฎที่ถูกเติมภายหลังในบรรทัด 3120–3122 กลับเขียนว่า:

```css
@media print {
  body:has(#member-card) .member-card { height: auto; min-height: 0; }
}
```

กฎนี้ override `height: 55mm` ทำให้ความสูงบัตรขึ้นกับเนื้อหาแทนที่จะล็อกตามมาตรฐานนามบัตรไทย ผลที่เป็นไปได้คือ:

- พรีวิวบนจอเป็นสัดส่วน 90:55 แต่ไฟล์/งานพิมพ์สูงไม่เท่ากัน
- ชื่อยาว รูป บาร์โค้ด QR และข้อความท้ายบัตรทำให้ความสูงเปลี่ยน
- บัตรหลายใบอาจมีขนาดหรือระยะตัดไม่สม่ำเสมอ

Batch print มีปัญหาแบบเดียวกันในเชิงสถาปัตยกรรม: preview ใช้ความกว้าง 360px แต่ print ใช้ 90mm; หากมี rule ที่ปล่อยความสูงตามเนื้อหา ความตรงกันระหว่าง preview กับ print จะเสียได้

### 5. ส่วน capture host ยังเป็นโค้ดเก่าที่ไม่ถูกใช้กับปุ่มดาวน์โหลดปัจจุบัน

`client/src/index.css` บรรทัด 992–1023 ยังมี `.member-card-capture-host` สำหรับ html2canvas แต่โค้ด `MemberCardModal` เปลี่ยนมาใช้ `window.print()` แล้ว จึงควรตัดสินใจให้ชัดว่าจะใช้แนวทางใดแนวทางหนึ่ง ไม่ควรเหลือ implementation สองชุดที่ให้ผลลัพธ์คนละแบบ

## ลำดับงานที่ควรให้ทีมแก้

### P0 — ต้องแก้ก่อนส่งให้ลูกค้าเทส

1. **แก้ dependency/lockfile ให้ติดตั้งใหม่ได้**
   - เพิ่ม/สร้าง `pnpm-lock.yaml` ให้ตรงกับ `package.json`
   - ยืนยันด้วย `pnpm install --frozen-lockfile`
   - รัน `pnpm check`, `pnpm test`, `pnpm build` ให้ผ่าน

2. **แก้ PDF ของ Reports ให้ตรงกับชื่อปุ่ม**
   - ปุ่ม `PDF` ต้องเรียก `await downloadReportPdf(state.doc)`
   - ปุ่ม `พิมพ์` เท่านั้นที่เรียก `printReportDoc(state.doc)`
   - อย่าปิด preview ก่อน `downloadReportPdf()` เสร็จ
   - กำหนดชื่อไฟล์ให้มี `.pdf` เพียงครั้งเดียวและทดสอบภาษาไทย/ตัวเลข/แถวรวม

3. **แยกการทำงานบัตรสมาชิกให้ชัดเจน**
   - `ดาวน์โหลด PDF`: สร้าง PDF ไฟล์จริงและเรียก download โดยตรง
   - `พิมพ์บัตรสมาชิก`: เปิด print flow เท่านั้น
   - ทั้งสองทางต้องใช้ source layout/config เดียวกัน เพื่อให้ขนาดและข้อมูลตรงกัน

4. **ล็อกขนาดบัตรทุก output เป็น 90×55 มม.**
   - ลบหรือแก้ rule `height: auto` ใน `@media print`
   - ให้ single card และ batch card ใช้ `width: 90mm; height: 55mm; box-sizing: border-box`
   - ห้ามให้เนื้อหาดันความสูงบัตร
   - ทดสอบชื่อสั้น/ชื่อยาว, มีรูป/ไม่มีรูป, มี card number/HN, barcode/QR พร้อมกัน

### P1 — ต้องทดสอบก่อนประกาศว่าเสร็จ

- ทดสอบ Export รายงานครบทุกแท็บที่มีปุ่ม: สรุปยอดขาย, ประวัติบิล, ธุรกรรมสมาชิก, สินค้าคงคลัง, ยอดเงินในบัตร
- ตรวจว่า CSV, Excel และ PDF ใช้ข้อมูลชุดเดียวกันกับ preview รวมถึง filter, date range, staff/member search และ totals
- ทดสอบ PDF หลายหน้าและข้อมูลเกิน 30 แถว
- ตรวจ PDF ด้วย `pdfinfo`/ภาพ render ว่าขนาด A4 ถูกต้องและไม่มีแถวตกหล่น
- ตรวจบัตรใบเดียวและ batch ว่าทุกใบเท่ากันจริงเมื่อวัดจาก PDF/งานพิมพ์
- ทดสอบ Chrome/Edge ที่ใช้ในเครื่องลูกค้า และตรวจ print scale ต้องเป็น 100% / Actual size

## ข้อสรุปสำหรับการตัดสินใจ

ตอนนี้ **ยังไม่ควร merge เข้า `main`** และยังไม่ควรส่งให้ลูกค้าเทสในฐานะเวอร์ชันพร้อมใช้งาน เพราะมีทั้ง blocker การติดตั้ง/build และพฤติกรรมปุ่ม Export/บัตรสมาชิกที่ไม่ตรงกับชื่อปุ่มและความต้องการเดิม

แนวทางที่ถูกต้องคือแก้ P0 บน `main-v2` เท่านั้น จากนั้นให้ตรวจ output จริงด้วยข้อมูลตัวอย่างก่อน แล้วค่อยขออนุมัติ merge เข้า `main` เมื่อผู้ใช้ยืนยันเอง
